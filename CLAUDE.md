# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server (Turbopack) at http://localhost:3000
- `npm run build` — production build (Turbopack)
- `npm start` — run the production build
- `npm run lint` — Biome check (lint + format check, no auto-fix)
- `npm run format` — Biome format, writes fixes in place
- `npx tsc --noEmit -p tsconfig.json` — type-check the project (no dedicated `typecheck` script exists)

There is no test framework configured in this repo (no test script, no Jest/Vitest/Playwright).

After any change, verify with `npx tsc --noEmit`, `npm run lint`, and `npm run build` — this project has caught real type/lint issues (e.g. MUI v9's `Stack` no longer types `alignItems`/`justifyContent` as direct props; pass them via `sx` instead) that only surface at type-check time.

## Architecture
Next.js 15 App Router + TypeScript. Path alias `@/*` maps to `./src/*`. Auth is wired to a real backend (see below) — there is no mock/local auth anymore.

**MUI wiring (`src/components/ThemeRegistry.tsx`)**: The app is NOT a default Next.js MUI setup — `src/app/layout.tsx` renders only `<html suppressHydrationWarning><ThemeRegistry bodyClassName={...}>{children}</ThemeRegistry></html>`; `ThemeRegistry` itself (not `layout.tsx`) renders the `<body>` tag, as an MUI `Box component="body"`. `ThemeRegistry` is a `"use client"` component that composes `AppRouterCacheProvider` (from `@mui/material-nextjs/v15-appRouter`) → `ThemeProvider` (theme from `@/theme`) → `CssBaseline` → the `body` `Box` → `NotificationProvider` → `children`. **The `body` Box must stay nested *inside* `AppRouterCacheProvider`, never a parent of it** — an earlier version rendered `Box component="body"` in `layout.tsx` above `ThemeRegistry`, which put it outside the Emotion `CacheProvider`'s context; Emotion silently fell back to its default (non-`compat`) cache for that node, which server-renders an inline `<style data-emotion="css ...">` that the client never reproduces, causing a real hydration-mismatch crash (not a false positive from browser extensions — confirmed by the `data-emotion` key being `css`, the default cache key, instead of `mui`). If you ever need to restructure root layout, keep every MUI-styled element as a descendant of `AppRouterCacheProvider`.

**Brand theme (`src/theme.ts`)**: a single `createTheme()` export holding the full design system — palette (warm gold primary, soft rose secondary, deep bronze text, cream linen background, muted sage support), typography (serif headings via `var(--font-playfair-display)`, sans body via `var(--font-montserrat)`), and component style overrides for `MuiButton`, `MuiOutlinedInput`, `MuiTextField`, `MuiCard`, `MuiPaper`. The two font CSS variables are generated by `next/font/google` in `layout.tsx` (`Montserrat`, `Playfair_Display`) and consumed here as `var(--font-*)` with literal-string fallbacks — if you rename a `next/font` `variable` in `layout.tsx`, update the matching string in `theme.ts` or the fonts silently fall back to the generic fallback chain. Prefer extending this file over ad-hoc `sx` overrides when a change should apply app-wide.

**Route structure**: `src/app/page.tsx` is still the untouched `create-next-app` starter page (not wired to anything). The real routes so far are all auth/account related, each a thin server `page.tsx` (metadata only) rendering a `"use client"` component under `src/components/`:
- `src/app/auth/login` → `LoginPage.tsx` (default export, not the `NotificationProvider`-style named export the rest use)
- `src/app/auth/qr/generator` → `src/components/auth/QrGeneratorView.tsx` — first-time 2FA setup (shows QR + secret, requires OTP confirm)
- `src/app/auth/qr/verify` → `src/components/auth/QrVerifyView.tsx` — 2FA challenge on every login (6-digit code entry, countdown, attempt limit)
- `src/app/account/security/otp` → `src/components/account/OtpResetView.tsx` — re-enroll 2FA for an already-logged-in user

New pages/routes should follow this pattern: route `page.tsx` stays a server component for metadata, real UI logic goes in a `"use client"` component under `src/components/`.

**Admin dashboard (`src/app/admin`, `src/components/admin/`)**: `src/app/admin/page.tsx` is the ADMIN role's home route (matches `getRoleHomeRoute`'s `ADMIN` → `/admin` in `src/lib/roles.ts`), rendering `AdminDashboardView.tsx`. It's a static, mock-data-driven dashboard — no API calls yet; every component takes its data via typed, optional props with mock defaults, so wiring a real endpoint later only means passing real props instead of the `mockData.ts` imports.
- `AdminLayout.tsx` is the reusable admin shell (`{ title, children }`): a standard MUI responsive-drawer layout — `AdminSidebar` rendered twice (`variant="permanent"` on `md+`, `variant="temporary"` with toggle below `md`), an `AppBar`/`Toolbar` with a mobile menu button, and a `Box component="main"` content area offset by the shared `DRAWER_WIDTH` constant it exports.
- `AdminSidebar.tsx` renders the "D Fleur" branding, a `NavItem[]` list (icon as a `"home" | "cart"` string key mapped locally to `@mui/icons-material` icons — kept string-based so nav data stays API-shaped, not JSX-shaped), an active-route pill state via `usePathname()`, and a bottom-anchored inline SVG botanical motif. The `Orders` item links to `/admin/orders`.
- `FinancialOverviewCard.tsx`, `RevenueLineChart.tsx`, `DebtBarChart.tsx` are the three dashboard cards (KPI grid + trend notes, revenue line chart, revenue-vs-debt bar chart). The two charts use `@mui/x-charts` (`LineChart`/`BarChart`) — the only chart library in the repo, added specifically for this page. Every color/typography value in these components (including chart series colors, gridlines, and legend text) is derived from `theme.ts` tokens via `useTheme()`/`alpha()`/`darken()`, never a new hardcoded hex — extend `theme.ts` instead of adding one-off colors here.
- `mockData.ts` is the single source of default/sample data, typed against interfaces owned by the components that use them (`FinancialMetric` in `FinancialOverviewCard.tsx`, `RevenueSeriesPoint` in `RevenueLineChart.tsx`, `DebtComparisonPoint` in `DebtBarChart.tsx`, `NavItem` in `AdminSidebar.tsx`) to avoid duplicate type definitions.
- Layout uses plain `Box` with `sx={{ display: "grid", gridTemplateColumns: {...} }}` rather than the MUI `Grid` component — `Grid`/`Grid2` has no prior usage in this codebase and its v9 API wasn't worth risking (same class of version-specific trap as the `Stack` gotcha noted above).

**Orders page (`src/app/admin/orders/page.tsx`, `src/components/admin/Orders*.tsx`)**: API-driven, unlike the still-mocked dashboard — `OrdersView.tsx` is the `"use client"` view wrapped in `<AdminLayout title="...">`, composing `OrdersFilterToolbar.tsx` (one always-single-row bar: a search box, a "Bộ lọc (n)" button, and icon-only New Order/Export/Print buttons — Export/Print are still `useNotification()` stubs; the "Bộ lọc" `Popover` holds the Status/Sales/Florist multi-selects and the two delivery date pickers with "Xóa"/"Áp dụng", so a wide set of filters never has to wrap in the ~900–1500px the toolbar gets beside the 280px drawer; all controls 40px tall, plain MUI `sx` — the repo has no Tailwind — plus removable filter chips + "Clear All" for the applied filters) and `OrdersTable.tsx` (an MUI X `DataGrid`, not a hand-rolled `Table` — `checkboxSelection`, `density="compact"`, `pageSizeOptions={[50, 100]}`, server-side pagination (`paginationMode="server"`, controlled `paginationModel`, `rowCount`), a custom `slots.footer` rendering "Page X of Y (Total N records)"). The table is a fixed-height box that scrolls internally, not the window: `OrdersView` sizes its `Stack` to `calc(100vh - ADMIN_CONTENT_CHROME)` (exported by `AdminLayout`, keep it in sync with the shell's top/bottom spacing), `OrdersTable` fills the space left under the toolbar (`flex: 1`, `minHeight: 420`) and the grid is **not** `autoHeight`, so its own sticky header row and the footer stay in view; the four sticky-left columns are plain CSS `position: sticky` (column pinning is Pro-only), which is why `disableVirtualization` stays on. One `headerBg` constant is set as `--DataGrid-t-header-background-base` and reused on the sticky header cells — DataGrid paints regular header cells from that variable, so setting only the sticky ones (as before) made them a different colour. This is the first page to need `@mui/x-data-grid` and `@mui/x-date-pickers` (+ `date-fns` as the `AdapterDateFns` peer dep) — both now in `package.json`, Community-tier features only (no column pinning/row grouping).
- `orderUtils.ts` owns the `Order`/`OrderStatus` types, `ORDER_STATUS_META` (status→label map: `pending`→"New", `done_process`→"Preparing", `done`→"Delivered", `cancelled`→"Cancelled"; chip colors are computed separately in `OrdersTable.tsx` via `useTheme()`'s stock `success`/`warning`/`info`/`error` slots, since `theme.ts` doesn't define brand-matched semantic colors), `replaceOrderByCode` (in-place row patch after an update), and `formatOrderDate`/`formatOrderTimeRange`/`formatVnd`, plus `getDeliveryWindow` (the table's "Ngày Giao"/"Giờ Giao" cells stay one line for a same-day window and add a second "→ end" line when start and end fall on different days). The backend's delivery-date fields (`deliveryDateStart`/`deliveryDateEnd`) come back as `"DD-MM-YYYYTHH:mm:ss+07:00"` — day/month swapped relative to real ISO 8601 — so `parseOrderDate()` rewrites the string before delegating to the native `Date` parser; never call `new Date(raw)` directly on these fields, it silently misparses. `salePrice`/`totalAmount` are VND integers, formatted via `formatVnd()` (`Intl.NumberFormat("vi-VN", { style: "currency", currency: "VND" })`).
- **Data flow** (`src/lib/api/orders.ts`, `useOrders.ts`, `useStaffOptions.ts`): `OrdersView` owns the *applied* `filters` + `paginationModel`, builds `OrderListParams`, and refetches whenever `buildOrderQuery(params)` changes (any applied-filter change resets to page 0). The toolbar stages edits in its own draft state and only calls `onFiltersChange` on the popover's "Áp dụng" button (or Enter / the arrow in the search box; closing the popover discards un-applied picks), so filtering never hits the server per keystroke/checkbox; chip delete and "Clear All" apply immediately. `getOrders()` hits `NEXT_PUBLIC_API_ADMIN_ORDER_LIST` with `startDate` (`DD-MM-YYYY`), `endDate` (end of day, `DD-MM-YYYY HH:mm:ss`), comma-joined `statuses`/`saleAccount`/`floristAccount` (comma-joined multi-select is **unverified** against the backend), and derives `rowCount = pageSize * totalPage` (the response has no total, so "Total N" overstates on the last page). `useOrders` guards list-vs-list ordering with a request-id ref and protects individual orders, not the whole array: a per-order try-lock (`pendingCodes`, a second status change on an order already in flight is dropped and its `StatusChip` is disabled; other rows are unaffected), and a per-row version merge on every list response (`mergeFetchedOrders`/`pickNewerOrder` in `orderUtils.ts`: a locked or higher-version local row wins, orders created via `addOrder` after the fetch started are re-inserted if the response lacks them). Status changes (`updateOrderStatusApi`, PUT) update the row only after success and bump `version`; an optimistic-lock conflict (`isStaleOrderError`: `record_have_been_updated`/`ERROR_OPT_001`) toasts and refetches. Sale/florist options come from `getSaleUsernames()` (ADMIN+SALE merged) / `getFloristUsernames()` via `NEXT_PUBLIC_API_ADMIN_EMPLOYEES_BY_ROLE`, failing soft to `[]`. Shared catch-block handling lives in `useApiErrorHandler()` (401 → `clearSession()` + `/`, else a Vietnamese toast). DataGrid's built-in column sort/filter still works but is client-side, i.e. current page only. Orders have no mock data anymore; `mockData.ts` now only holds the dashboard's still-mocked data (nav items, financial metrics, charts).
- **Order form (create + update)**: `OrderFormModal.tsx` (full-screen `Dialog` + `AppBar`; uses `slots={{ transition }}`, not the deprecated `TransitionComponent`; an optional `dirty` prop makes closing ask "Bỏ các thay đổi chưa lưu?" first) hosts `OrderForm.tsx`, which is mode-agnostic: it gets `initialValues`, `onSubmit`, `successMessage`, labels, `requireChange`, `resetOnSuccess`, `onStale`, `onDirtyChange` and owns its state through `useOrderForm.ts`. The form domain lives in `orderForm.ts` (options, `OrderFormValues`, money helpers, `computeOrderTotals`, `validateOrder`, `buildOrder`, `orderToFormValues`, `areOrderFormValuesEqual`, `rebaseOrderFormValues`); `orderUtils.ts` keeps the API model, status, dates, list/merge helpers. `submit()` runs `validateOrder()` — field-level (`{ field: message }`, inline `error`/`helperText` + a toast of the first message; existing rules plus discount ≤ list price, deposit ≤ total, valid dates, ≤ 10 images) — then uploads **only the `File` entries** of `images` (`(string | File)[]`: an existing URL or a new file, in display order — no parallel URL array) via `uploadSampleFiles()` (`src/lib/api/upload.ts`): a pool of `UPLOAD_CONCURRENCY` (3) concurrent `uploadSampleFile()` calls that **joins** before resolving — URLs come back in the order of `images`, not completion order, and `onSubmit` (create/update) only runs once every upload has succeeded. On a failure no new upload starts, in-flight ones finish, the first error is thrown (nothing is created/updated) and finished uploads stay in a `WeakMap` cache, so the retry re-uploads only the missing files — then `buildOrder()` → the `onSubmit` prop. Any failure keeps the modal and typed values. Sale/florist are multi-select `Autocomplete`s over `useStaffOptions()` (`saleAccounts`/`floristAccounts: string[]`, comma-joined on the wire; accounts already on the order but missing from the staff list stay selectable). Money inputs are raw digit strings (`toDigits`/`formatMoneyInput`); totals come from `computeOrderTotals()` (florist-fe rules: delivery fee counts only when the customer pays, options 1/2; VAT applies to the fee only for option 2). Outgoing dates must go through `formatOrderDateString()` (inverse of `parseOrderDate`), never `toISOString()`. `dirty` compares values the way the payload would differ (text trimmed, money by number). Image limits (jpeg/png/webp, ≤4MB, ≤10) live in `ORDER_IMAGE_LIMITS`.
- **Create**: the toolbar's "New Order" button opens `OrderFormModal` → `OrderForm` with `createEmptyOrderFormValues()`; `OrdersView` wires `onSubmit` to `createOrderApi()` and the returned order is inserted by `useOrders.addOrder` (`insertOrderSorted`: delivery start desc, then end desc) with no list refetch and no page jump (falls back to `refresh()` only if the response has no `orderCode`). Success resets the form (`resetOnSuccess`), notifies and scrolls back to the top — the modal stays open until the user closes it. The payload has no `orderCode`/`status`/`version` (backend assigns them); an empty social link is sent as `"none"`.
- **Update** (click the order code in the table → `OrderUpdateModal.tsx`): `useOrderDetail(code)` GETs `NEXT_PUBLIC_API_ADMIN_ORDER_DETAIL/<code>` (fresh `version`) each time the modal opens, `orderToFormValues()` seeds the form, save is disabled until something changed. `onSubmit` → `useOrders.saveOrder()` → `updateOrderApi()` (PUT `NEXT_PUBLIC_API_ADMIN_ORDER_UPDATE`, sends the full order with `orderCode`, the **loaded** `version`, the unchanged `status`, and `editor` = `getAccount()` from `src/lib/storage.ts` — the username stored at login, else the JWT `sub`). `saveOrder` takes the same per-order lock as a status change (a save on an order with a change in flight is rejected with `ORDER_BUSY`), then patches the row **in place by `orderCode`** (`replaceOrderByCode`: keeps its position, no list refetch; the row's `version` becomes `max(response, sent + 1)`). A stale conflict (`isStaleOrderError`) keeps the modal open, toasts, reloads the detail (`onStale`), refreshes the grid row (`syncOrder`) and **rebases the user's draft** onto the fresh copy (`rebaseOrderFormValues`: untouched fields take the server's value, the user's edits are kept, fields changed by both sides keep the user's value and are named in a dismissible alert). Editing an order with no images requires adding one (`validateOrder` rule, same as create). An edited order that no longer matches the active filters stays visible until the next fetch.

**Real-time order sync over SSE (`src/lib/api/orderSse.ts`, `src/providers/OrderNotificationProvider.tsx`, `src/lib/notificationStore.ts`)**: the backend pushes `ORDER_CREATED`/`ORDER_UPDATED` events over `GET /notification/v1/order/subscribe` (`NEXT_PUBLIC_API_ORDER_SUBSCRIBE`, ADMIN/SALE only, tenant-scoped via the JWT) so the admin Orders page updates live without polling.
- **Transport**: `@microsoft/fetch-event-source` with `Authorization: Bearer <token>`, not the native `EventSource` (which can't set headers) — `subscribeOrderEvents()` in `orderSse.ts` wraps it, treats 401/403 as fatal (stops retrying, calls `onFatal`), and lets anything else (including the backend's normal 5-minute connection cap) retry silently via the library's own backoff. There's no event replay/`Last-Event-ID` support server-side, so every reconnect *after* the first calls `onReconnect` — the only correct response to that is a full refetch, since anything missed while disconnected is gone for good.
- **Provider placement gotcha**: `OrderNotificationProvider` wraps `AuthProvider` in `ThemeRegistry.tsx` (`NotificationProvider > OrderNotificationProvider > AuthProvider > children`), *not* nested inside it as you'd naively expect from "auth-gated feature." `AuthProvider` (`src/providers/AuthProvider.tsx`) returns `null` and re-runs its check effect on every pathname change — nesting the SSE provider inside it would silently tear down and reconnect the one-per-tab stream on every navigation. `OrderNotificationProvider` has no auth context to consume either way, so it reads `readStoredRoles()`/the access token straight from `localStorage`, gated by the new `hasAnyRole()` helper (`src/lib/roles.ts`) against `["ADMIN", "SALE"]`, re-evaluated on `storage` (cross-tab) and `focus` (same-tab) events.
- **`useOrders.ts` internals are a `Map<orderCode, Order>` + a separately maintained sorted `orderCode[]` + a cached `Map<orderCode, DeliverySortKey>`** (`orderUtils.ts`'s `computeDeliverySortKey`/`findSortedInsertIndex`), not a flat array — replacing the old `insertOrderSorted`/`replaceOrderByCode`/`mergeFetchedOrders`. The public `orders: Order[]` (for the DataGrid) is derived via `useMemo` keyed on a `revision` counter that's bumped once per mutation (or once per *batch*, see below), not recomputed on every render. The point of caching the sort key isn't really the Map's O(1) lookup (at 50-100 rows per page that's noise) — it's that the old code re-sorted the *entire* array with `.sort()` on every single insert, and the comparator re-parsed `deliveryDateStart`/`deliveryDateEnd` (regex + `Date` construction) on every comparison; caching the key once per order turns binary-search insertion into plain number comparisons. Removal from the sorted array is a deliberate plain `indexOf` (O(n)), not a symmetric binary search — the comparator's ties (same delivery time) make exact-identity binary removal a correctness hazard, and removal is comparatively rare next to lookups.
- **Event-burst "cool down"**: `OrderNotificationProvider` buffers incoming events in a ref and flushes them as a batch on a trailing ~200ms timer, not one at a time — bounds re-renders, `localStorage` writes, and toast spam to once per window regardless of burst size (e.g. a bulk import). `useOrders`'s `applyOrderEvents(events, activeFilters)` takes the whole batch, mutates the Map/array per event with no intermediate `bump()`, then bumps exactly once. A flushed batch over 3 events collapses into one summary toast ("N đơn hàng mới, M đơn hàng vừa cập nhật") instead of one per event; the notification drawer still persists each individually (only the toast is collapsed) via `notificationStore.ts`'s batch `addNotifications()`.
- **Self-echo dedup by trace ID, not by actor**: the user's own create/update/status-change still produces its own SSE-driven toast (not suppressed by comparing `actor`), but showing *both* that and the direct REST-success toast for the same action would be a visible duplicate. The trace ID is **read from the backend's own mutation response**, not client-generated — a client-generated `X-Trace-Id` sent on the request was tried and confirmed *not* honored by the backend (it generates its own ID regardless of what's sent), so that approach was reverted. `createOrderApi`/`updateOrderApi`/`updateOrderStatusApi` (`src/lib/api/orders.ts`) all now return `{ traceId }` (create/update also return `{ order, traceId }`) read from the response body, and `useOrders.saveOrder`/`useOrders.changeStatus`/`OrdersView.handleCreateOrder` call `OrderNotificationProvider`'s `claimTraceId(traceId)` right after a successful response — first arrival (REST success or the SSE flush) wins the claim, the other stays silent. `updateOrderStatusApi` participating in this at all is the actual fix here: it used to discard its whole response body (`Promise<void>`) and never claim anything, so every status change unconditionally double-toasted. `claimTraceId` is a `Map<traceId, expiresAt>` ref (~15s TTL); an SSE event whose `traceId` is already claimed is silently excluded from `toSurface` (no toast/OS notification), but state sync (`applyOrderEvents`) always runs for every event regardless, since it's idempotent by `version`. Because the claim only happens after the response resolves, a slow REST call can still in principle lose the race to a fast SSE echo (buffered up to 200ms) — accepted as a known edge case, not solved, since the backend doesn't support closing it any other way from the frontend alone.
- **Edit-modal conflict handling reuses the existing stale-save machinery**, it doesn't duplicate it: when an `ORDER_UPDATED` event arrives for the `orderCode` currently open in `OrderUpdateModal`, `OrdersView` passes it down as `externalUpdate` (a prop threaded through, since there's no other global "which order is being edited" signal — `useOrders` only tracks it via `editingCodeRef`/`setEditingCode` for the SSE wiring's own use). `OrderUpdateModal.tsx`'s `OrderUpdateContent` patches the background row (`syncOrder`) and swaps its form's source from the loaded `order` to the SSE-delivered copy (`freshFromSse`) — producing a new `initialValues` object is enough to trigger `useOrderForm.ts`'s existing identity-watching effect, which runs `rebaseOrderFormValues` and shows the same conflict banner (`OrderForm.tsx`) already used for the stale-version-on-save case. No changes were needed in `useOrderForm.ts`/`OrderForm.tsx` for this.
- **Persistence** (`notificationStore.ts`): `STORAGE_KEYS.NOTIFICATIONS` in `localStorage`, 24h TTL filtered lazily on read (not actively swept), capped at 200 entries, wiped by `clearAuthStorage()` (full logout) but not `clearSession()` (mid-OTP-flow). The bell + unread `Badge` sits in `AdminLayout.tsx`'s `Toolbar`; `NotificationDrawer.tsx` is a third `Drawer` (`anchor="right"`) alongside the two nav drawers, ticking a local timer every 60s while open so TTL-expired entries visibly drop off without needing a new event.
- **Native OS notifications** (`src/lib/browserNotification.ts`): every event that wins the trace-ID claim in `flush()` also fires a Web Notification API popup (Windows Action Center / Ubuntu libnotify, via whatever browser is running), alongside the toast — not gated on `document.hidden`, so it fires even while the tab is focused. This is the plain `Notification` API only, no Service Worker/Push subscription, so it stops working the moment the tab or browser is closed (no backend push infra exists for that). `ensureNotificationPermission()` is called (harmlessly repeatable — a no-op once granted/denied) from the same role/token `evaluate()` effect that gates the SSE connection, so the permission prompt appears as soon as an eligible user is detected. Each notification's `tag` is the event's `traceId` (or a synthetic `batch-<timestamp>` for the collapsed-summary case), so the OS also de-dupes/replaces rather than stacking popups for the same event.
- **Assumptions not verified against a live backend** (confirm before relying on them): `NEXT_PUBLIC_API_ORDER_SUBSCRIBE` uses `NEXT_PUBLIC_FLORIST_URL` like the other order endpoints even though its path is `/notification/v1/...` not `/admin/v1/order/...`; `matchesOrderFilters`' `search` substring match (`orderCode`/`customerName`/`customerPhone`/`receiverName`/`receiverPhone`) is a best-effort guess at the backend's real semantics. (Confirmed, not an open assumption: the backend does return a top-level `traceId` on the create/update/status mutation responses, and generates that ID itself — a client-supplied `X-Trace-Id` header is ignored, which is why the dedup above reads the ID from the response rather than sending one.)

**Auth flow (`src/lib/api/`, `src/lib/storage.ts`, `src/lib/roles.ts`)**: login is a two-step, backend-driven flow, not a client-only mock:
1. `LoginPage.tsx` calls `loginApi()` (`src/lib/api/auth.ts`) with username/password. On success it stores the returned `otpToken` in `localStorage` (`STORAGE_KEYS.OTP_TOKEN`) and routes to `/auth/qr/generator` (first-time setup) or `/auth/qr/verify` (has 2FA already), based on the `requiredGenerateOTP` flag in the response.
2. Both QR views call `otpGenerateApi()`/`otpVerifyApi()`/`otpLoginApi()`, all authenticated with the OTP token (not a bearer access token) via the `authorization` option on `postJson`. On final success (`otpLoginApi`), `accessToken`/`refreshToken`/`roles` are stored and the OTP token is cleared; the user is routed by `getRoleHomeRoute(roles)` (`src/lib/roles.ts` — `ADMIN`→`/admin`, `MANAGER`→`/manager`, else `/user`; none of these role-home routes exist yet).
3. `OtpResetView.tsx` mirrors the generate/verify pair but authenticates with `Bearer <accessToken>` instead of the OTP token, for a logged-in user resetting their authenticator. Its comment in `src/lib/api/auth.ts` flags this as unconfirmed with backend — the reset flow reuses the same generate/verify endpoints as first-time setup rather than dedicated "reset MFA" endpoints, pending confirmation.

All API calls go through the helpers in `src/lib/api/client.ts` (`postJson`, `getJson`, `putJson`, `postFormData`), which throw a typed `ApiError { code, status }` on non-2xx responses (`code` read from the response body's `errorCodes[0]`, falling back to a per-call default). `src/lib/api/errors.ts` maps error codes to Vietnamese user-facing strings via `ErrorMessage.getMessage(code)` (or `useApiErrorHandler()` in components) — always route caught `ApiError`s through this rather than showing `error.message` directly. A `401` (or `OTP_TOKEN_MISSING`/`OTP_RATE_LIMITED`) mid-flow clears the relevant session keys (`clearSession()` or a manual `removeItem`) and bounces to `/`.

Session state (`accessToken`, `refreshToken`, `roles`, `OTP_TOKEN`, `tenant`) lives in `localStorage` only (`src/lib/storage.ts`'s `STORAGE_KEYS`) — there's no cookie/server-session layer, so every client component that depends on auth state reads `localStorage` directly and must guard for SSR (`typeof window === "undefined"`, as `getTenant`/`readStoredRoles` already do).

API endpoint URLs are env-driven (`NEXT_PUBLIC_API_LOGIN`, `NEXT_PUBLIC_API_LOGIN_WITH_OTP`, `NEXT_PUBLIC_API_OTP_GENERATE`, `NEXT_PUBLIC_API_OTP_VERIFY`, `NEXT_PUBLIC_API_ADMIN_ORDER_LIST`/`_ORDER_CREATE`/`_ORDER_STATUS`/`_ORDER_DETAIL`/`_ORDER_UPDATE`, `NEXT_PUBLIC_API_ADMIN_EMPLOYEES_BY_ROLE`, `NEXT_PUBLIC_UPLOAD_FILE` — `.env` is tracked and holds the full list; `.env.example` lists only the orders/upload vars), read via `requireEnv()` which throws loudly if a var is missing rather than silently hitting `undefined`. Being `NEXT_PUBLIC_*`, these are inlined at build time and visible client-side — fine for endpoint URLs, but never put a secret behind this prefix.

**Shared QR/auth UI**: `src/components/auth/AuthPageShell.tsx` is the common glassmorphism card wrapper (title + centered `Paper`) for all post-login-page auth screens — reuse it for new auth/account pages instead of rebuilding the layout. `src/components/qr/QRGenerator.tsx` (renders the QR via `react-qr-code`, extracts/copies the TOTP secret from the QR URL's `secret` query param, and collects the 6-digit confirm OTP) is shared by both `QrGeneratorView` and `OtpResetView`. `src/components/qr/CodeVerification.tsx` is the 6-box digit-entry UI used by `QrVerifyView` for the login-time challenge.

**Notifications (`src/providers/NotificationProvider.tsx`)**: app-wide `Snackbar`/`Alert` feedback is centralized here, not implemented per-page. It's mounted once in `ThemeRegistry` (inside the `body` Box, wrapping `children`) and exposes `useNotification()` returning `notify(message, severity?, options?)`. Internally it holds a FIFO queue of `{ message, severity, autoHideDuration }` so notifications fired close together (e.g. from different components) display one after another instead of one clobbering another — call `notify(...)` from any client component instead of adding a local `Snackbar` to a page.

**`src/components/LoginPage.tsx`** is a self-contained full-screen glassmorphism login form (background image + blurred `::before` overlay, translucent `Paper` card) with local `useState` for form fields/errors/loading, on-submit validation (required + min-length), and a real `loginApi()` call (see the auth flow above) that calls `useNotification().notify(...)` for error feedback and routes to the appropriate 2FA step on success. Note it's a `default export` unlike the auth/account view components, which are named exports.

Note: `<html lang="vi">` is currently set to Vietnamese — check with the user before changing locale-dependent behavior.
