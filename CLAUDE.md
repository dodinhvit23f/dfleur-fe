# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server (Turbopack) at http://localhost:3000
- `npm run build` — production build (Turbopack)
- `npm start` — run the production build
- `npm run lint` — Biome check (lint + format check, no auto-fix)
- `npm run format` — Biome format, writes fixes in place
- `npx tsc --noEmit -p tsconfig.json` — type-check the project (no dedicated `typecheck` script exists)

There is no test framework configured in this repo (no test script, no Jest/Vitest/Playwright).

After any change, verify with `npx tsc --noEmit`, `npm run lint`, and `npm run build` — this project has caught real type/lint issues (e.g. MUI v9's `Stack` no longer types `alignItems`/`justifyContent` as direct props; pass them via `sx` instead) that only surface at type-check time.

## Architecture
Next.js 15 App Router + TypeScript. Path alias `@/*` maps to `./src/*`. Auth is wired to a real backend (see below) — there is no mock/local auth anymore.

**MUI wiring (`src/components/ThemeRegistry.tsx`)**: The app is NOT a default Next.js MUI setup — `src/app/layout.tsx` renders only `<html suppressHydrationWarning><ThemeRegistry bodyClassName={...}>{children}</ThemeRegistry></html>`; `ThemeRegistry` itself (not `layout.tsx`) renders the `<body>` tag, as an MUI `Box component="body"`. `ThemeRegistry` is a `"use client"` component that composes `AppRouterCacheProvider` (from `@mui/material-nextjs/v15-appRouter`) → `ThemeProvider` (theme from `@/theme`) → `CssBaseline` → the `body` `Box` → `NotificationProvider` → `children`. **The `body` Box must stay nested *inside* `AppRouterCacheProvider`, never a parent of it** — an earlier version rendered `Box component="body"` in `layout.tsx` above `ThemeRegistry`, which put it outside the Emotion `CacheProvider`'s context; Emotion silently fell back to its default (non-`compat`) cache for that node, which server-renders an inline `<style data-emotion="css ...">` that the client never reproduces, causing a real hydration-mismatch crash (not a false positive from browser extensions — confirmed by the `data-emotion` key being `css`, the default cache key, instead of `mui`). If you ever need to restructure root layout, keep every MUI-styled element as a descendant of `AppRouterCacheProvider`.

**Brand theme (`src/theme.ts`)**: a single `createTheme()` export holding the full design system — palette (warm gold primary, soft rose secondary, deep bronze text, cream linen background, muted sage support), typography (serif headings via `var(--font-playfair-display)`, sans body via `var(--font-montserrat)`), and component style overrides for `MuiButton`, `MuiOutlinedInput`, `MuiTextField`, `MuiCard`, `MuiPaper`. The two font CSS variables are generated by `next/font/google` in `layout.tsx` (`Montserrat`, `Playfair_Display`) and consumed here as `var(--font-*)` with literal-string fallbacks — if you rename a `next/font` `variable` in `layout.tsx`, update the matching string in `theme.ts` or the fonts silently fall back to the generic fallback chain. Prefer extending this file over ad-hoc `sx` overrides when a change should apply app-wide.

**Route structure**: `src/app/page.tsx` is still the untouched `create-next-app` starter page (not wired to anything). The real routes so far are all auth/account related, each a thin server `page.tsx` (metadata only) rendering a `"use client"` component under `src/components/`:
- `src/app/auth/login` → `LoginPage.tsx` (default export, not the `NotificationProvider`-style named export the rest use)
- `src/app/auth/qr/generator` → `src/components/auth/QrGeneratorView.tsx` — first-time 2FA setup (shows QR + secret, requires OTP confirm)
- `src/app/auth/qr/verify` → `src/components/auth/QrVerifyView.tsx` — 2FA challenge on every login (6-digit code entry, countdown, attempt limit)
- `src/app/account/security/otp` → `src/components/account/OtpResetView.tsx` — re-enroll 2FA for an already-logged-in user

New pages/routes should follow this pattern: route `page.tsx` stays a server component for metadata, real UI logic goes in a `"use client"` component under `src/components/`.

**Admin dashboard (`src/app/admin`, `src/components/admin/`)**: `src/app/admin/page.tsx` is the ADMIN role's home route (matches `getRoleHomeRoute`'s `ADMIN` → `/admin` in `src/lib/roles.ts`), rendering `AdminDashboardView.tsx`. It's a static, mock-data-driven dashboard — no API calls yet; every component takes its data via typed, optional props with mock defaults, so wiring a real endpoint later only means passing real props instead of the `mockData.ts` imports.
- `AdminLayout.tsx` is the reusable admin shell (`{ title, children }`): a standard MUI responsive-drawer layout — `AdminSidebar` rendered twice (`variant="permanent"` on `md+`, `variant="temporary"` with toggle below `md`), an `AppBar`/`Toolbar` with a mobile menu button, and a `Box component="main"` content area offset by the shared `DRAWER_WIDTH` constant it exports.
- `AdminSidebar.tsx` renders the "D Fleur" branding, a `NavItem[]` list (icon as a `"home" | "cart"` string key mapped locally to `@mui/icons-material` icons — kept string-based so nav data stays API-shaped, not JSX-shaped), an active-route pill state via `usePathname()`, and a bottom-anchored inline SVG botanical motif. The `Orders` item links to `/admin/orders`.
- `FinancialOverviewCard.tsx`, `RevenueLineChart.tsx`, `DebtBarChart.tsx` are the three dashboard cards (KPI grid + trend notes, revenue line chart, revenue-vs-debt bar chart). The two charts use `@mui/x-charts` (`LineChart`/`BarChart`) — the only chart library in the repo, added specifically for this page. Every color/typography value in these components (including chart series colors, gridlines, and legend text) is derived from `theme.ts` tokens via `useTheme()`/`alpha()`/`darken()`, never a new hardcoded hex — extend `theme.ts` instead of adding one-off colors here.
- `mockData.ts` is the single source of default/sample data, typed against interfaces owned by the components that use them (`FinancialMetric` in `FinancialOverviewCard.tsx`, `RevenueSeriesPoint` in `RevenueLineChart.tsx`, `DebtComparisonPoint` in `DebtBarChart.tsx`, `NavItem` in `AdminSidebar.tsx`) to avoid duplicate type definitions.
- Layout uses plain `Box` with `sx={{ display: "grid", gridTemplateColumns: {...} }}` rather than the MUI `Grid` component — `Grid`/`Grid2` has no prior usage in this codebase and its v9 API wasn't worth risking (same class of version-specific trap as the `Stack` gotcha noted above).

**Orders page (`src/app/admin/orders/page.tsx`, `src/components/admin/Orders*.tsx`)**: API-driven, unlike the still-mocked dashboard — `OrdersView.tsx` is the `"use client"` view wrapped in `<AdminLayout title="...">`, composing `OrdersFilterToolbar.tsx` (search, delivery date-range pickers, Status/Sales/Florist multi-selects, removable filter chips + "Clear All", icon-only Export/Print buttons still wired to `useNotification()` stubs, and an icon-only "New Order" button) and `OrdersTable.tsx` (an MUI X `DataGrid`, not a hand-rolled `Table` — `checkboxSelection`, `density="compact"`, `pageSizeOptions={[50, 100]}`, server-side pagination (`paginationMode="server"`, controlled `paginationModel`, `rowCount`), a custom `slots.footer` rendering "Page X of Y (Total N records)"). This is the first page to need `@mui/x-data-grid` and `@mui/x-date-pickers` (+ `date-fns` as the `AdapterDateFns` peer dep) — both now in `package.json`, Community-tier features only (no column pinning/row grouping).
- `orderUtils.ts` owns the `Order`/`OrderStatus` types, `ORDER_STATUS_META` (status→label map: `pending`→"New", `done_process`→"Preparing", `done`→"Delivered", `cancelled`→"Cancelled"; chip colors are computed separately in `OrdersTable.tsx` via `useTheme()`'s stock `success`/`warning`/`info`/`error` slots, since `theme.ts` doesn't define brand-matched semantic colors), the create-form helpers below, and `formatOrderDate`/`formatOrderTimeRange`/`formatVnd`. The backend's delivery-date fields (`deliveryDateStart`/`deliveryDateEnd`) come back as `"DD-MM-YYYYTHH:mm:ss+07:00"` — day/month swapped relative to real ISO 8601 — so `parseOrderDate()` rewrites the string before delegating to the native `Date` parser; never call `new Date(raw)` directly on these fields, it silently misparses. `salePrice`/`totalAmount` are VND integers, formatted via `formatVnd()` (`Intl.NumberFormat("vi-VN", { style: "currency", currency: "VND" })`).
- **Data flow** (`src/lib/api/orders.ts`, `useOrders.ts`, `useStaffOptions.ts`, `useDebouncedValue.ts`): `OrdersView` owns `filters` + `paginationModel`, builds `OrderListParams`, and refetches whenever `buildOrderQuery(params)` changes (search is debounced 400ms; any filter change resets to page 0). `getOrders()` hits `NEXT_PUBLIC_API_ADMIN_ORDER_LIST` with `startDate` (`DD-MM-YYYY`), `endDate` (end of day, `DD-MM-YYYY HH:mm:ss`), comma-joined `statuses`/`saleAccount`/`floristAccount` (comma-joined multi-select is **unverified** against the backend), and derives `rowCount = pageSize * totalPage` (the response has no total, so "Total N" overstates on the last page). `useOrders` guards against out-of-order responses with a request-id ref. Status changes (`updateOrderStatusApi`, PUT) update the row only after success and bump `version`; an optimistic-lock conflict (`isStaleOrderError`: `record_have_been_updated`/`ERROR_OPT_001`) toasts and refetches. Sale/florist options come from `getSaleUsernames()` (ADMIN+SALE merged) / `getFloristUsernames()` via `NEXT_PUBLIC_API_ADMIN_EMPLOYEES_BY_ROLE`, failing soft to `[]`. Shared catch-block handling lives in `useApiErrorHandler()` (401 → `clearSession()` + `/`, else a Vietnamese toast). DataGrid's built-in column sort/filter still works but is client-side, i.e. current page only. Orders have no mock data anymore; `mockData.ts` now only holds the dashboard's still-mocked data (nav items, financial metrics, charts).
- **Create-order modal**: the toolbar's "New Order" button (`onNewOrder`) opens `OrderFormModal.tsx` (full-screen `Dialog` + `AppBar`; uses `slots={{ transition }}`, not the deprecated `TransitionComponent`) containing `OrderForm.tsx`, which owns its state through `useOrderForm.ts` — so closing the modal unmounts the form and reopening gives a blank one. `submit()` runs `validateOrder()` (first error → `notify`) → uploads images sequentially via `uploadSampleFile()` (`src/lib/api/upload.ts`: multipart `file` to `NEXT_PUBLIC_UPLOAD_FILE`, Bearer accessToken, response `{ data: url }`; already-uploaded files are cached in a `WeakMap` so a retry after a later failure doesn't re-upload) → `buildOrder()` (a `CreateOrderPayload` — no `orderCode`/`status`/`version`, the backend assigns them; empty social link is sent as `"none"`) → the `onSubmit` prop, which `OrdersView` wires to `createOrderApi()` and then refetches (jumping to page 1). Success resets the form, notifies and scrolls back to the top — the modal stays open until the user closes it (`onSuccess` is optional); any failure keeps the modal and typed values. Money inputs are raw digit strings (`toDigits`/`formatMoneyInput`); totals come from `computeOrderTotals()` (ported from florist-fe's rules: delivery fee counts only when the customer pays, options 1/2; VAT applies to the fee only for option 2). Outgoing dates must go through `formatOrderDateString()` (the inverse of `parseOrderDate`), never `toISOString()`. Sale/florist inputs are `Autocomplete`s over the staff lists from `useStaffOptions()`. Image limits (jpeg/png/webp, ≤4MB, ≤10) live in `ORDER_IMAGE_LIMITS`.

**Auth flow (`src/lib/api/`, `src/lib/storage.ts`, `src/lib/roles.ts`)**: login is a two-step, backend-driven flow, not a client-only mock:
1. `LoginPage.tsx` calls `loginApi()` (`src/lib/api/auth.ts`) with username/password. On success it stores the returned `otpToken` in `localStorage` (`STORAGE_KEYS.OTP_TOKEN`) and routes to `/auth/qr/generator` (first-time setup) or `/auth/qr/verify` (has 2FA already), based on the `requiredGenerateOTP` flag in the response.
2. Both QR views call `otpGenerateApi()`/`otpVerifyApi()`/`otpLoginApi()`, all authenticated with the OTP token (not a bearer access token) via the `authorization` option on `postJson`. On final success (`otpLoginApi`), `accessToken`/`refreshToken`/`roles` are stored and the OTP token is cleared; the user is routed by `getRoleHomeRoute(roles)` (`src/lib/roles.ts` — `ADMIN`→`/admin`, `MANAGER`→`/manager`, else `/user`; none of these role-home routes exist yet).
3. `OtpResetView.tsx` mirrors the generate/verify pair but authenticates with `Bearer <accessToken>` instead of the OTP token, for a logged-in user resetting their authenticator. Its comment in `src/lib/api/auth.ts` flags this as unconfirmed with backend — the reset flow reuses the same generate/verify endpoints as first-time setup rather than dedicated "reset MFA" endpoints, pending confirmation.

All API calls go through the helpers in `src/lib/api/client.ts` (`postJson`, `getJson`, `putJson`, `postFormData`), which throw a typed `ApiError { code, status }` on non-2xx responses (`code` read from the response body's `errorCodes[0]`, falling back to a per-call default). `src/lib/api/errors.ts` maps error codes to Vietnamese user-facing strings via `ErrorMessage.getMessage(code)` (or `useApiErrorHandler()` in components) — always route caught `ApiError`s through this rather than showing `error.message` directly. A `401` (or `OTP_TOKEN_MISSING`/`OTP_RATE_LIMITED`) mid-flow clears the relevant session keys (`clearSession()` or a manual `removeItem`) and bounces to `/`.

Session state (`accessToken`, `refreshToken`, `roles`, `OTP_TOKEN`, `tenant`) lives in `localStorage` only (`src/lib/storage.ts`'s `STORAGE_KEYS`) — there's no cookie/server-session layer, so every client component that depends on auth state reads `localStorage` directly and must guard for SSR (`typeof window === "undefined"`, as `getTenant`/`readStoredRoles` already do).

API endpoint URLs are env-driven (`NEXT_PUBLIC_API_LOGIN`, `NEXT_PUBLIC_API_LOGIN_WITH_OTP`, `NEXT_PUBLIC_API_OTP_GENERATE`, `NEXT_PUBLIC_API_OTP_VERIFY`, `NEXT_PUBLIC_API_ADMIN_ORDER_LIST`/`_ORDER_CREATE`/`_ORDER_STATUS`, `NEXT_PUBLIC_API_ADMIN_EMPLOYEES_BY_ROLE`, `NEXT_PUBLIC_UPLOAD_FILE` — `.env` is tracked and holds the full list; `.env.example` lists only the orders/upload vars), read via `requireEnv()` which throws loudly if a var is missing rather than silently hitting `undefined`. Being `NEXT_PUBLIC_*`, these are inlined at build time and visible client-side — fine for endpoint URLs, but never put a secret behind this prefix.

**Shared QR/auth UI**: `src/components/auth/AuthPageShell.tsx` is the common glassmorphism card wrapper (title + centered `Paper`) for all post-login-page auth screens — reuse it for new auth/account pages instead of rebuilding the layout. `src/components/qr/QRGenerator.tsx` (renders the QR via `react-qr-code`, extracts/copies the TOTP secret from the QR URL's `secret` query param, and collects the 6-digit confirm OTP) is shared by both `QrGeneratorView` and `OtpResetView`. `src/components/qr/CodeVerification.tsx` is the 6-box digit-entry UI used by `QrVerifyView` for the login-time challenge.

**Notifications (`src/providers/NotificationProvider.tsx`)**: app-wide `Snackbar`/`Alert` feedback is centralized here, not implemented per-page. It's mounted once in `ThemeRegistry` (inside the `body` Box, wrapping `children`) and exposes `useNotification()` returning `notify(message, severity?, options?)`. Internally it holds a FIFO queue of `{ message, severity, autoHideDuration }` so notifications fired close together (e.g. from different components) display one after another instead of one clobbering another — call `notify(...)` from any client component instead of adding a local `Snackbar` to a page.

**`src/components/LoginPage.tsx`** is a self-contained full-screen glassmorphism login form (background image + blurred `::before` overlay, translucent `Paper` card) with local `useState` for form fields/errors/loading, on-submit validation (required + min-length), and a real `loginApi()` call (see the auth flow above) that calls `useNotification().notify(...)` for error feedback and routes to the appropriate 2FA step on success. Note it's a `default export` unlike the auth/account view components, which are named exports.

Note: `<html lang="vi">` is currently set to Vietnamese — check with the user before changing locale-dependent behavior.
